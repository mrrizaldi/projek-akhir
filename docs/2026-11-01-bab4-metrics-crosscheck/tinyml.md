Research date: 1 November 2026. Scope: Chapter 4 of buku-pa, `tab:sumber-daya`, `tab:beban-komputasi`, `tab:uji-kesetaraan-tahap`.
All source PDFs/documents are in `laporan/pustaka/belum-dirujuk/riset-pengukuran/tinyml/` (together with the `.txt` files produced by `pdftotext -layout`).
Page number = PDF page number (`pdftotext` form-feed separator), unless stated otherwise.

## 0. What our code actually measures (read from `firmware/test/test_inference/test_inference.cpp`)

Inspecting the code shows several things not yet written in Chapter 4. They are relevant for the defense:

- Latency: `micros()` brackets one `interpreter->Invoke()` per beat, 7 beats (indices 2–8), one run. On the installed arduino-esp32 (3.20017), `micros()` = `esp_timer_get_time()` (`cores/esp32/esp32-hal-misc.c:166-168`), so the resolution is 1 µs. The code **already prints the mean and the maximum** (`test_latency_and_memory`), but the book reports only the mean.
- The warm-up **already happened by accident**. `RUN_TEST(test_diagnostic_golden_input)` runs before the latency test and calls `Invoke()` 9 times (7 beats, zero input, beat 2). As a result the 26.6 ms measurement is not a cold inference. This fact is not yet written down and can be used as an argument.
- Arena: `alignas(16) static uint8_t tensor_arena[24*1024]` lives in internal SRAM (.bss), not PSRAM. `arena_used_bytes()` is read after `AllocateTensors()`.
- Preprocessing load: `us_run / GOLDEN_N` is the total busy time divided by the number of samples. The replay runs back to back without 360 Hz pacing, so the 82 µs figure is an **aggregate utilization** (busy time / available time), not a per-call mean. The peak `us_max` is the maximum observed over 2,400 calls.
- The Arduino loop runs on core 1 (`CONFIG_ARDUINO_RUNNING_CORE 1`). The WiFi task is pinned to core 0 (`CONFIG_ESP32_WIFI_TASK_PINNED_TO_CORE_0=y`, `tools/sdk/esp32s3/sdkconfig:233,1242`).

## 3. Most important gaps (ordered by defense risk)

1. **The 26.6 ms latency comes from 7 inferences with no repetitions and no spread.** The standard references (MLPerf Tiny/EEMBC) ask for ≥ 10 seconds and ≥ 10 iterations, 5 runs, the median, and a warm-up. MLPerf Inference uses p90. This is the easiest question for an examiner. The fix is cheap: one test with N = 1,000 on the board, about 30 seconds, reporting median/p99/max. Meanwhile, the max from the 7 beats is already printed by the code, and the de facto warm-up (the 9 earlier `Invoke()` calls) can be mentioned.
2. **On-device INT8 equivalence is only 7 beats of one recording without class S.** The MEAN bug proves that silent failure is real, and MLPerf computes accuracy on the DUT over the whole validation set. Fix: hundreds to a thousand DS2 windows (including S) streamed to the board, then report label agreement and the quantum difference. Separate the bit-exact kernel test (identical int8 input) from the tolerance-based chain test.
3. **The real-time load was measured for 6.67 seconds, as a replay, without WiFi, and partly still on the 250 window.** The 33.4 ms peak is the maximal observed, not the WCET (Wilhelm). The criterion queue < capacity is conceptually right (Liu & Layland A2), but it needs a long run with a body signal and WiFi+MQTT. Data to record: histogram, p99, queue high-water mark, lost samples.
4. **Latency and load with WiFi active are not measured, and the literature is empty too.** The only handle is the ESP-IDF document (WiFi priority 23 on core 0, loop on core 1). An A/B test of WiFi OFF vs ON+MQTT with the same statistics closes the limitation already written in the book. The result is also an original contribution.
5. **Runtime peak memory is not reported.** There is only the build .data/.bss and an instantaneous heap. No standard requires it, so the risk is moderate. However, `ESP.getMinFreeHeap()` and the stack high-water mark after a long run with WiFi are just two log lines and answer the question "what is the peak RAM?".

Conformance notes that are **already strong** and defensible: the latency comparator against 200 ms is stricter than the literature (Tran uses 400 ms); the arena via `arena_used_bytes` matches how TFLM itself does it; the Δ threshold relative to float32 is in line with MLPerf Inference ("within 1% of the FP32 reference"); the staged equivalence test is stricter than all the ECG papers read, because Tran and Berki only assume PC = MCU.
